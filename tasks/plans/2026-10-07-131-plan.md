# Issue #131 - Stop reading the Drinkability Index as maturity: Implementation Plan

**Status:** implemented, PR open - approved 2026-10-07 - D1-A, D2-A, D3-A, D4 yes (all recommended). plan-review skipped by maintainer.
**Branch:** `fix/131-drinkability-index`
**Issue:** https://github.com/slavins-co/cellartracker-mcp/issues/131

## Summary

`drinking-recommendations` labels wines "PAST PEAK — drink now!" whenever `Available > 1.0`, and that check overrides the listed drinking window. `Available` turns out not to be a maturity measure. It is CellarTracker's **Drinkability Index**: bottles you "should have drunk by now" on a curve across the window, minus the bottles you actually drank. It is counted in bottles and grows with how many you bought. A value of 1.47 means "about one and a half bottles behind CT's pace". It says nothing about peak.

I checked this against CT's own docs and the real export. The `Linear` column matches the documented formula exactly for all 51 in-window rows. `Available` always equals one of the seven curve columns, picked by wine type: Early Bell for most dry whites, which is why both whites in the repro read high.

The fix:
- The listed window drives the maturity label.
- The index is shown as what it is, a pacing number, and never produces a verdict.
- Labels describe and stop instructing.
- The raw index and the window bounds go into the structured output.
- The sort order runs on the window.
- The skill docs that teach the wrong meaning get corrected.

Patch bump to 0.5.2. Open the PR, no release.

## Open Decisions

### D1. Should "PAST PEAK" stay in the output at all?

- **A (recommended): drop the phrase.** A wine past its listed window gets "Past listed window (2024)".
  - Pro: this is the strongest claim the data supports.
  - Pro: a listed window ending is also a weak signal, not proof the wine has faded.
  - Con: a wine that really is gone gets no stronger flag than "past window".
- **B: your original rule.** Allow "PAST PEAK" only when the current year is past `EndConsume` AND the index agrees.
  - Con: with the real semantics, the AND adds no independent evidence. CT adds a +100 penalty to the index whenever the window has ended and bottles remain. So "the index agrees" fires exactly when the window has ended. B would say PAST PEAK on the window alone, which is the thin-data verdict you ruled out.
  - Pro: it keeps a loud flag for the long-expired case.

One related change: your example label "CT availability index says late" doesn't match what the index measures. It measures consumption pace, not lateness. I'd keep the index out of the status string entirely and show it on its own line: `Pacing: CT drinkability index +1.47 (bottles behind CT's drinking-pace curve)`. That still reports both signals, and the status never mixes them.

### D2. What should `drinkingPriority` sort on?

- **A (recommended): window first, index as tie-breaker.**
  - Order: past listed window (oldest end first) → final year of the window → rest of the window (earliest end first) → window not yet open → no data.
  - Within a tier, a higher index sorts first.
  - Pro: the order follows the strongest signal we have.
  - Pro: it isn't skewed toward wines you bought by the case.
- **B: index first, relabelled "behind pace".** This is how CT's own Ready to Drink report sorts.
  - Pro: it's faithful to CT.
  - Con: the index scales with bottle count, so a 12-bottle holding outranks a single bottle in its last year.
  - Con: for a cellar with mostly 1-3 bottles of each wine, it's mostly noise.

### D3. Should the test fixtures use the real wine names and iWine IDs?

The repo CLAUDE.md says to keep personal details out of fixtures, and what's in your cellar is borderline personal.

- **A (recommended): anonymize the identity, keep the real numbers.** For example "2019 Chardonnay", window 2023-2028, 2 on hand / 1 consumed, `Available` 1.46944751381215.
  - Pro: the regression value is the same, and nothing about your cellar goes public.
- **B: use the real names and iWine IDs, as you asked.** The catalog data is public, but the fixture then shows what you own.

### D4. Should the skill docs be fixed in this PR? (scope addition)

`skills/cellartracker-data/SKILL.md` and `references/schema.md` tell the model "`Available` > 1.0 - Past peak, drink ASAP". That's the same bug in the docs layer, and it reaches callers even when they skip this tool.

- **Recommended: yes, in this PR.** It's a small diff, and fixing only the code leaves the model re-deriving "past peak" from the raw field.

## Detailed Plan

Written so a fresh session can pick this up without the original conversation. Read `tasks/lessons.md` first.

### Background a fresh session needs

- **Source of the definition:** https://support.cellartracker.com/article/28-ready-to-drink-report
  - `% Window Used = days into window / total days`
  - `Should Have Consumed = % Window Used * (on hand + pending + consumed)`
  - `Index = Should Have Consumed - consumed`
- **Reading the index:**
  - Negative means drinking faster than pace, or the window hasn't opened yet.
  - Positive and at most the bottles remaining means about that many bottles will be left when the window closes.
  - Greater than the bottles remaining means the window has ended with bottles left. CT adds a 100-point penalty that grows over time.
- **Curve per wine type (CT docs):**
  - Late Bell: red Bordeaux, Northern Rhône, Rioja
  - Twin Peak: red Southern Rhône, white Northern Rhône, white German
  - Fast Aging: rosé, Beaujolais, Moscato d'Asti
  - Standard Bell: other reds
  - Early Bell: other dry whites
  - `Available` equals the curve column CT assigned to the wine. The export doesn't name which curve was used.
- **Verification already done (2026-10-07, real export):**
  - `Linear` equals the formula for 51/51 in-window rows (max diff 0.0).
  - `Available` equals at least one curve column on 64/64 rows.
  - Range is -0.92 to 1.59, and only 2 rows are above 1.0, both whites in mid-window.
- **Repro rows** (use the numbers; identity per D3):
  - 2019 Chardonnay:
    - Window 1/1/2023-12/31/2028 (List: 2023/2028), Source Personal
    - Inventory 2, Consumed 1, Pending 0
    - `Available` = `Early` = 1.46944751381215, `Linear` 0.882701962574167
  - 2024 Sauvignon Blanc:
    - Window 1/1/2025-12/31/2027 (List: 2025/2027), Source Personal
    - Inventory 2, Consumed 0, Pending 0
    - `Available` = `Early` = 1.588, `Linear` 1.17733089579525
- **Latent bug to fix along the way:**
  - In the Availability table, `EndConsume`/`BeginConsume` are `M/D/YYYY`. In the List table they are bare years.
  - `crossReference` keeps the List value when it's present. When it's empty, the Availability value fills in.
  - Then `Math.floor(parseFloat("12/31/2028"))` gives `12`, so the wine reads as "window closing (12)".
  - The year parse needs to handle both formats.
